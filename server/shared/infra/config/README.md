# shared/infra/config —— amad 的配置加载

一份配置结构，一个文件来源：**读 `AMA_CONFIG` 指向的 YAML 文件（默认 `config.yaml`）**，
再用环境变量覆盖。

```
环境变量  >  YAML 文件  >  内置默认值
```

```
AMA_CONFIG=<路径>       配置文件路径，默认 config.yaml
```

**配置文件路径本身只从环境变量读**：要先知道去哪拿配置，才能拿到配置，
把这一项放进配置文件会变成鸡生蛋。

文件读不到或解析失败就直接退出，不静默回落——回落会让「所有配置都是内置默认值」
看起来一切正常。

## 多份 YAML 叠加

`ParseLayers` 支持按顺序叠加多份 YAML（后者里**非空**的字段覆盖前者），方便把密钥
单独放一份文件。`cmd/amad` 目前只读一份。

叠加靠的是 `yaml.Decode` 到同一个结构体是**合并**语义（没提到的字段保持原值，
不会被零值抹掉）——这是依赖库的行为，所以有单测专门钉住它
（`TestParseLayersMergesInsteadOfReplacing`）。

## 环境变量为什么留在最高优先级

线上出事时改一个环境变量重启即恢复；密钥（`AMA_PG_PASSWORD` / `AMA_REDIS_PASSWORD` 等）
也可以只放环境变量、不进文件。

**代价**是「改了文件却没生效」，而且不报错。为此 `Result.EnvOverridden` 会列出所有被
环境变量盖掉的字段名，`cmd/amad` 在启动日志里打出来：

```
INFO 配置已加载 source=config.yaml store=pg
WARN 以下字段被环境变量覆盖了 —— 改配置文件对它们无效，要改环境变量 fields=[pg.host pg.password ...]
```

只打字段名不打值——密钥不能进日志。

## 配置启动时加载一次，不热替换

候选的四个「看起来能热更新」的字段，在现有代码里一个都不是动态读的——

| 字段 | 实际读法 |
| --- | --- |
| `server.allowedOrigin` | `httpd.Server{cfg Config}` 是值拷贝，`cors()` 读 `s.cfg` |
| `server.devRoutes` | 路由**注册时**就定了 |
| `docker.*` / `worker.concurrency` | `WorkerPool.Run` 启动时建好 `dockertools.Provider` 与 worker 池 |
| `auth.*` | `auth.New` 启动时读一次（OIDC 客户端、限流参数、管理员名单） |

要让它们真能热更新，得改四个模块、每处都重新论证并发安全，**收益与风险不成比例**。
而一个「只对边缘字段生效、其余静默无效」的热更新机制，正是本仓库反复踩的
「设了但没生效」那类坑的温床。所以配置**启动时加载一次、之后只读**，改配置走重启。

## 为什么不用 viper

viper 的隐式行为——自动搜索路径、`AutomaticEnv`、配置热重载——和本仓库「薄封装、
显式、无魔法」的取向冲突：出问题时你不知道值是从哪来的。这里就是 `yaml.Decode` +
一个显式的环境变量覆盖函数，读代码就能确定每个值的来源。

同理，下游包**不自己 `os.Getenv` 读业务配置**，由 `cmd/amad` 显式传入（如 `core.WorkerConfig`）。
自己读的问题是：配置换了来源之后它们读不到，而症状只出现在最远端，报错不指向
「配置没传进来」。唯一的例外是 `shared/infra/docker`：`docker.host` 留空时它读 `DOCKER_HOST`，
与 docker CLI 同一套约定。Docker 段各键与对应环境变量见
[docs/guides/docker-executor.md](../../../../docs/guides/docker-executor.md)。

## ⚠️ 未知字段只告警，不致命（配置可以先于代码上线）

YAML 里出现结构体不认识的字段时，**服务照常启动**，那些字段进 `Result.UnknownFields`，
由 `cmd/amad` 在启动日志里打一条 WARN。

这里曾经是 `KnownFields(true)` 直接报错，理由是防「键名拼错 → 以为设了其实没设」。
但那条规则把**配置与代码的上线顺序**变成了硬约束：配置里加了新字段、而认识它的
Go 代码还没上线时，二进制解析失败 → 进程退出 → 反复重启。**配置是全局的，所以全部
实例都起不来，没有任何实例活下来。**

「配置先加字段、代码随后上线」是完全正常的操作顺序；**滚动发布与回滚期间新旧二进制
并存时更是必然**——老实例一定会读到新字段。让它变成故障是错的取舍，未知字段该有的
处理是「这个版本还不认识它，忽略」。

拼错键名那个坑仍然守着，只是降级成启动日志里的一条 WARN，而不是一次线上事故。
所以**清理/改配置后记得扫一眼启动日志有没有这条 warn**——它现在是发现手误的唯一途径。

仍然致命的是**类型不匹配**（`port: not-a-number`）与 YAML 语法错误：那些放过去会静默
变成零值，比起不启动更难查。三条测试分别钉住这三种情况，且都做过变异验证。

## 测试

全部离线（`config_test.go` + `source_test.go`）。重点锁的是那几件「错了不报错」的事：
分层合并、环境变量优先级与覆盖清单、配置文件路径的取法、未知字段被记账但不阻止启动
（对**每一层**都生效）、以及类型错误仍然致命。
